Real-Time Stock Analysis Pipeline with Data Fusion
2.1 Objective:
The objective of this project is to design and implement a real-time data pipeline that aggregates and
analyzes different types of stock market data. The system will use separate microservices running in Docker
containers for data generation/movement (one for real-time prices, one for fundamental data) and a third
service for data fusion, processing, and visualization. This project will demonstrate how to containerize
data-intensive services, fuse heterogeneous data sources (real-time vs. static), and present the combined
analysis in a unified, interactive dashboard.

2.2 Functional Requirements:
1. The project must be implemented using at least three distinct Docker containers: a Price Polling
Service, a Fundamental Data Service, and an Analysis and Visualization Service.
2. The Price Polling Service must automatically fetch (generate/move) time-series price data (e.g., 5-
minute intervals) for at least three different stock tickers from a public financial API (e.g., Alpha
Vantage, Finnhub, or Yahoo Finance).
3. The Fundamental Data Service must automatically fetch (generate/move) company-specific financial
metrics (e.g., P/E Ratio, Market Cap, or 52-week high) for the same stock tickers.
4. The Analysis and Visualization Service must consume data from the other two services, performing
Data Fusion by linking the real-time price data with the fundamental data.
5. This service must perform Data Processing by calculating at least one technical indicator for each stock
(e.g., a 20-period Simple Moving Average (SMA) or Relative Strength Index (RSI)).
6. The Analysis and Visualization Service must host a visual dashboard that allows a user to select a stock
ticker and view its time-series price, the calculated technical indicator, and its fundamental metrics all
on one screen.

2.3 Non-Functional Requirements:
1. The entire 3-container application stack must be automated and launched using an Infrastructure as
Code (IaC) tool, such as Docker Compose, for consistent orchestration.
2. The data schemas for all data in motion (price data, fundamental data) and the complete data pipeline
must be clearly defined, visualized, and explained in the technical documentation.
3. The system must include robust error handling for API failures (e.g., rate limiting, invalid ticker, or
network errors) and log these events without crashing any of the services.
4. The price data on the dashboard should be ”near real-time,” with data being no more than 15 minutes
old.
5. The dashboard must be responsive, clear, and must load in under 10 seconds.
6. All communication between containers must be clearly defined (e.g., via REST API calls, a message
queue, or a shared database volume).
